# V4 反馈决策表（Feedback Decision Table）

## 〇、先说清楚来源（这一节很重要）

本站的反馈入口与留言板是 V4 才上线的，**截至 2026-10-06 还没有收到任何外部访客的反馈**（真后端查询结果为 0 条，我自己的测试数据已清理干净）。

所以下表的条目**不冒充访客反馈**：每一条都标注真实来源，其中绝大多数是**我自己的复现与自测**（桌面 1440 视口、手机 375 视口、代码走查、发布前检查清单）。等真实的同伴互测意见进来，直接往这张表里追加行即可 —— 表的列就是为追加设计的。

来源标注规则：
- `自测·桌面` / `自测·手机` / `自测·代码` / `自测·发布前`
- `同伴互测`（目前 0 条）
- `访客留言`（目前 0 条）

分类与优先级口径：先归因（Understand → Classify），再按 **影响 × 成本** 排（Prioritize），最后只做四种决定之一：**Accept（改） / Modify（换个做法改） / Delay（先记着） / Reject（不改）**。

## 二、这次**没有**做的改动（以及为什么）

| 想法 | 决定 | 理由 |
| --- | --- | --- |
| 给迭代区块的图片加 `loading="lazy"` | Delay | 4 张图合计约 236 KB、位置在首屏下方，收益有限；现在动它会牵动导出脚本、同步和整页截图三条链路，性价比不高。记为"下次继续加图时的第一步优化"。 |
| 换用 `supabase-js` | Reject | 站点只需要"写一条、读一列"，原生 `fetch` 打 PostgREST 就够，还能避免引入第三方库和额外体积。这是**刻意偏离**，不是偷懒。 |
| 把留言板做成需要登录 | Reject | 匿名墙的意图就是"路过的朋友随手写一句"；防滥用靠 RLS 只允许 INSERT、不允许改删，而不是加门槛。 |
| 在报告里把自测说成"访客反馈" | Reject | 不实。反馈不足就如实写"目前 0 条"，并把自测发现单列来源。 |

## 三、真实反馈进来之后怎么处理

1. 逐条登记到上表（来源写清是同伴互测还是访客留言）；
2. 先归因、再判定"是不是真问题"，**能复现才动手**（D-01 就是反例教材）；
3. 按影响 × 成本排，四种决定里必须选一个，**Delay / Reject 都要写理由**；
4. 改完跑 `docs\V4-回归测试清单.md` 里的六项回归；
5. 在迭代区块里加一张卡片，把"改了什么、为什么"留在站点上。
