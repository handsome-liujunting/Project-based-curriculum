# V3.5 反馈后台接入说明（Supabase）

> 面向：站点的作者（也就是你）。
> 目标：让右下角「提个意见」按钮真正把访客的反馈存进数据库。
> 现状：**前端已经全部写好并自测通过**，只差填两行配置 + 建一张表。
> 关联文件：`docs/V3.5-建表与RLS.sql`、`outputs/personal-homepage-v35/js/feedback-config.js`

---

## 0. 一句话流程

建项目 → 跑 SQL → 抄两个值填进配置 → 本地提交一条测试反馈 → 删掉测试数据 → 完事。

预计 15 分钟。不写后端代码、不装依赖。

---

## 1. 新建 Supabase 项目

1. 打开 <https://supabase.com/>，用 GitHub 或邮箱注册登录（免费档够用）。
2. **New project**：
   - `Name`：例如 `liujunting-homepage`
   - `Database Password`：点 **Generate a password**，然后**立刻存到密码管理器**
     （这个密码只用于直连数据库，**永远不需要填进网页**）
   - `Region`：选离你近的（如 `Southeast Asia (Singapore)`）
3. 等 1–2 分钟，项目初始化完成。

> 免费档注意：长期无访问的项目会被暂停，不影响数据。需要时可手动恢复。

---

## 2. 建表 + 开 RLS

1. 左侧 **SQL Editor** → **New query**。
2. 把 `docs/V3.5-建表与RLS.sql` 的**全文**粘进去 → **Run**。
3. 期望结果：`Success. No rows returned.`

脚本做了四件事：建 `feedback` 表（含长度护栏）、开启 RLS、只给匿名访客 INSERT 权限、建时间索引。
**没有**任何读取权限 → 满足「反馈不会公开，只有我能看到」。

⭐ **务必跑完再往下走**：表不存在时，网页提交会报 `relation "feedback" does not exist`。

---

## 3. 复制两个值

左侧 **Project Settings** → **API Keys**（新版叫 **API**，路径略有差异）：

| 需要的东西 | 界面上叫什么 | 长什么样 |
|---|---|---|
| 项目地址 | `Project URL` | `https://abcdefghijklmn.supabase.co` |
| 公开密钥 | `publishable key`（旧项目叫 `anon public` / `anon key`） | 新版 `sb_publishable_...`；旧版是很长的 `eyJ...` JWT |

- **结尾不要带 `/`**。
- 这两个值**本来就设计成给浏览器用的**，写进前端是正常的、也是安全的。

🚫 **绝对不要复制的两个东西**：`secret key`（旧称 `service_role`）和 **Database Password**。
它们能绕过 RLS —— 等于把整个后台交给所有访客。它们不该出现在这个仓库的任何文件里。

## 4. 填配置（只改这一个文件）

打开 `outputs/personal-homepage-v35/js/feedback-config.js`：

```js
window.FEEDBACK_CONFIG = {
  url: "https://abcdefghijklmn.supabase.co",   // ← 你的 Project URL（不带结尾斜杠）
  anonKey: "sb_publishable_xxxxxxxxxxxx",      // ← 你的 publishable key
  table: "feedback",                            // 与建表脚本一致，不用改
  siteVersion: "V3.5",                          // 提交时自动附带，不用改
  timeoutMs: 12000                              // 不用改
};
```

填完保存即可，**其他文件一行都不用动**。

> 站点上线后要发布新版本时，把 `siteVersion` 改成新版本号（如 `V3.6`），
> 之后收到的反馈就会自带这一版标记，方便对应到"哪一版出的问题"。

## 5. 本地自测

### 5.1 一条命令自检（推荐先跑这个）

配置填好后，在仓库根目录跑：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\check_feedback.ps1 -Post
```

它会依次做 5 件事，全部通过才会打印 `RESULT: all checks passed`：

| 步 | 检查 | 期望 |
|---|---|---|
| 1/5 | `feedback-config.js` 里的 `url` 形状 | `https://<项目>.supabase.co`（结尾不带斜杠） |
| 2/5 | `anonKey` 形状 | `sb_publishable_...`（打印时只显示前后几位） |
| 3/5 | **匿名能不能读** | 返回 `[]` —— 读到数据就说明 RLS 没生效 |
| 4/5 | 插入一条带标记的测试行 | `HTTP 201` |
| 5/5 | 打印标记 + 清理 SQL | 拿标记去 Table Editor 里核对 |

⭐ 第 4 步的标记（形如 `SELFCHECK-20260920-225900`）是**故意**做成唯一的：
按课件第 28 页的要求，**光看网页提示"提交成功"不算验收**，必须回数据库里找到同一条记录才算。

核完删掉它（脚本会把这条 SQL 原样打出来）：

```sql
delete from public.feedback where message = 'SELFCHECK-20260920-225900';
```

> 这个脚本只以**访客身份**说话（用 publishable key 走 REST 接口），
> 不碰你的数据库密码、也不要求任何高权限密钥。
> 默认只接受 `https://<项目>.supabase.co`；`-AllowAnyHost` 是给自测假后端用的开关，正常接入别加。

### 5.2 页面上手工测（4 项）

```powershell
# 在仓库根目录起一个本地静态服务，然后浏览器打开 http://127.0.0.1:8123/
```

**测试 A：正常提交**
1. 点右下角黄色「提个意见」按钮 → 弹出表单。
2. 填：称呼留空 / 关系选「同学」/ 设备选「电脑」/ 内容写「测试：本地自测」。
3. 点「提交反馈」→ 期望提示 **「收到啦，谢谢你的意见！」**，表单被清空。

**测试 B：必填校验**
- 内容留空直接提交 → 「内容还是空的，写一句话就能提交。」
- 内容填了但设备没选 → 「选一下这条反馈是在哪种设备上遇到的吧。」
- 两种情况页面都不会跳走、内容不会丢。

**测试 C：没填配置时（把你刚填的两行临时清空再试）**
- 打开表单会看到提示条：「后台还没配置好 —— 现在填写的内容暂时发不出去，配置完就能用了。」
- 点提交 → 「后台还没配置好，这条没发出去，内容我帮你留在框里了。」
- ⭐ 这是**故意**的：宁可明说通道没接好，也**不假装提交成功**。

**测试 D：关闭方式**
- 右上角 `×`、点灰色遮罩、按 `Esc` —— 三种都应能关闭，且焦点回到「提个意见」按钮。

## 6. 到数据库里确认

左侧 **Table Editor** → 选 `feedback` 表，或回到 SQL Editor 跑：

```sql
select id, name, relation, device, left(message, 60) as message_head, version, created_at
  from public.feedback
 order by created_at desc
 limit 20;
```

应该看到刚才那条测试记录，`version` 是 `V3.5`、`created_at` 是服务端时间。

**顺手做一次匿名视角验证（重要）**，确认访客读不到别人的反馈：

```powershell
# 把 <项目> 和 <publishable key> 换成你自己的
curl "https://<项目>.supabase.co/rest/v1/feedback?select=*" `
     -H "apikey: <publishable key>"
```

期望结果是 `[]`（空数组），**不是**数据列表。若真能读出数据，说明 RLS 没生效，回到第 2 节检查策略。

确认无误后删掉测试数据：

```sql
delete from public.feedback where message like '%测试%';
```

## 7. 日常看反馈 / 导出

- **看**：Table Editor → `feedback`，按 `created_at` 倒序。
- **导出**：Table Editor 右上角导出 CSV；或用 SQL Editor 的导出按钮。
  CSV 可直接用 Excel 打开（注意选 UTF-8，避免中文乱码）。
- **要不要做管理页面**：不需要。看反馈是你自己的事，用 Supabase 控制台足够了 ——
  前端多一个读取权限就多一分风险。

## 8. 安全红线（课件第 21 页）

| 规则 | 说明 |
|---|---|
| publishable / anon key 可以公开 | 它只能在 RLS 允许的范围内行动 |
| secret / service_role key 绝不进前端 | 它**绕过 RLS**，泄露等于后台全开 |
| 数据库密码绝不进前端 | 同上，且它是直连数据库的凭据 |
| 数据库里不留"公开读"的口子 | 本方案只有一条 INSERT 策略，没有 SELECT |
| 万一泄露了怎么办 | 立刻去 Project Settings → API Keys **轮换（Reset）密钥**，旧密钥立即作废 |

本仓库已有一道自动检查（`tools/verify_v35.ps1` 第 8 节）：
它会扫描 `feedback-config.js` 的**代码部分**（注释除外），
若出现 `eyJ...` 形式的 JWT、`service_role`、`SUPABASE_SERVICE` 等字样会直接报错。

## 9. 报错对照表

提交失败时页面会把错误写在按钮旁边（格式：`没提交成功，内容我帮你留着了…（HTTP 401 · …）`）。
对着下表查：

| 现象 | 原因 | 处理 |
|---|---|---|
| `HTTP 401` + `Invalid API key` | key 抄错 / 多空格 / 用了 secret key | 重新复制 publishable key |
| `HTTP 401` / `new row violates row-level security policy`（代码 42501） | 策略没建，或策略的 role 不对 | 重跑建表脚本第 2 节（策略应对 `anon` 与 `authenticated` 都开放 INSERT） |
| `HTTP 404` + `relation "feedback" does not exist` | 表没建 / 表名不一致 | 重跑建表脚本；核对 `table` 名 |
| `HTTP 404` + `PGRST205` | `url` 里多写了 `/rest/v1` | URL 只填到 `supabase.co` 为止 |
| 请求一直转圈然后超时 | 网络 / 项目被暂停 | 检查 Supabase 项目状态；`timeoutMs` 默认 12 秒 |
| 浏览器控制台报 CORS | 通常是 `url` 拼错（写成了别的域名） | 核对 `url` 与 Project URL 完全一致 |
| 提示「后台还没配置好」 | 两行配置为空或格式不对（`isConfigured()` 要求以 `http(s)://` 开头且不含 `YOUR_`） | 检查是否漏了引号、是否还残留 `YOUR_` 占位 |

## 10. 如果你以后不想用 Supabase

前端只依赖一个约定：**向一个 HTTPS 地址 POST 一段 JSON**。
所以换成别的表单服务（Formspree、Getform、自建接口）时，唯一要改的是
`feedback-config.js` 里的地址与请求头拼装方式，页面结构、样式、交互都不用动。
最省事的替代是**表单服务的直达 URL**，但要注意：第三方免费档通常会在免费额度、
数据归属、隐私条款上有额外限制 —— 作为课程作业，Supabase 的可控性更好。
